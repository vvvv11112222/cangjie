# 2026-10-10 CPU 耗时排查与视觉验收边界

## 本轮范围

仅修改视觉模型运行方式、CPU 配置和诊断工具。前端页面已恢复队友提交版本；Go 行为接口及公共协议扩展仍是本地草稿，未作为团队交付上传。本轮不启用显卡推理、不修改驱动或系统注册表。

模型、输入尺寸、每秒检查 2 次、80 人上限、行为门槛、姿态归属检查和再次裁剪均保留。规则文件 `behavior.py` 与原移植版本摘要一致。

## 时间用在哪里

Windows 11，AMD Ryzen 9 8940HX，16 核、32 逻辑处理器。实际模型执行器均为 `CPUExecutionProvider`；CPU 报告的活动显卡为 null。使用同一 640×360 密集课堂片段中的 1 秒范围，实际分析 2 张画面；两个进程顺序运行，各自重新加载模型。

| 项目 | 修改前 | CPU 2 线程 | CPU 4 线程 |
| --- | --- | --- | --- |
| 本地处理总时间（含转码和导出） | 37.62 秒 | 23.24 秒 | 14.56 秒 |
| 模型初始化 | 1.13 秒 | 0.92 秒 | 0.84 秒 |
| 检测阶段 | 0.185 秒 | 0.367 秒 | 0.214 秒 |
| 姿态阶段 | 33.333 秒 | 20.258 秒 | 12.120 秒 |
| 头姿阶段 | 1.611 秒 | 0.852 秒 | 0.592 秒 |

修改前：姿态占总时间约 88.6%，模型初始化约 3%。大姿态模型实际运行 124 次，原 CPU 路径受 GPU 单线程配置影响，只用了 1 个推理线程。实际观察 94 人次，初次裁剪、归属不符的再次裁剪和完整人体检查使调用次数多于人数；不能通过删除这些步骤充当无损提速。

修复 CPU 与 GPU 线程配置混用，所有 CPU 模型使用独立配置；关闭空闲线程忙等待，避免多个模型线程池争用。常规模式的小姿态模型延迟到实际使用时加载。选择 4 线程 CPU 配置，批次仍为 1，未增加并发视频任务。

线程配置参考 [ONNX Runtime 官方线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。不同机器应重新测量，不能据此推导固定提速比例。

## 结果对照

- 两张画面的 94 次人物记录在编号、框位置（容差 0.001 像素）、行为、座位、姿态可用性和站立状态上相同；人数时间线、事件和相关统计均相同。
- 再用同一 4 秒密集片段分析 8 张画面，CPU 4 线程本地处理 54.55 秒。372 次人物记录的编号、位置和四种行为均与此前 CPU 接口测试结果相同；人数时间线和事件相同。
- 此前 4 秒测试的 156.44 秒包含实际 HTTP 接入，新 54.55 秒为本地分析和导出，不能把两者直接作为端到端提速比例。
- 初始化、精度和输入检查没有跳过；姿态仍调用 499 次，低头头姿调用 242 次。

以上仅证明这些画面的结果一致，不能证明所有视频准确率不变，也没有达到 2 分钟录像在 2 分钟内完成的目标。没有运行整节课堂的 CPU 或 GPU 性能验收。

## 远处目标与标注

对已有 30 秒密集课堂报告进行离线统计，不重新加载模型：61 张画面、2888 次人物观察。其中 880 次头部宽高最小值不足 16 像素（约 30.5%），举手可判断比例约 33.9%，低头可判断比例为 0。这里统计的是画面是否能判断，不是识别准确率；像素大小也不等同于实测距离。

报告有 87 个匿名编号、17 个编号仅出现一次、15 个座位关联过多个编号。这是遮挡或编号变化的排查线索，不能直接断言同一个学生被重复编号，也不能当作 87 个学生。

本地建立了近景两张画面的开发检查标签：共 12 次人物观察，初步标出 4 次举手，现有报告全部找到。这些标签由 Codex 看图初标，需真人核对；不是独立留出集。缺少可靠低头正例，不能计算低头召回率。真实图片、标签和逐人记录保留在忽略的 `var/`，不进入 Git。

下一阶段应补充密集教室的完整标注、低头正例、托腮与摸头负例、侧脸和遮挡案例。保持开发集与留出验收集分开，分别报告误判、漏检、无法判断比例、持续动作时间误差和编号变化。

## 复现入口

从仓库根目录运行，使用已安装 Worker 依赖的 Python 3.12：

```powershell
python -m workers.tools.profile_cpu <受控短录像.mp4> var/cpu-diagnosis --duration-s 1 --threads 4
python -m workers.tools.audit_visual_report <已有本地report.json> --output var/observation-audit.json
python -m workers.tools.check_vision_quality <开发或留出集标签.json>
```

CPU 诊断强制关闭所有显卡推理，拒绝超过 31 秒的输入；分析范围最多 4 秒，总处理期限最多 240 秒。Windows 空闲内存不足 2 GB 时不启动，低于 768 MB 时停止后续模型调用。资源检查只能在模型调用之间生效，不能打断正在运行的单次 ONNX 调用。

输出中的 `profile.json` 分别记录模型加载、推理次数、实际执行器和 CPU 线程数；`report.json` 保留原算法的行为与时间证据。不同配置必须用同一录像和分析范围，输出到不同目录；不允许覆盖既有结果。
