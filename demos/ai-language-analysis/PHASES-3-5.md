# 第三至五阶段实现记录

## 第三阶段：转写修订与报告版本

原始 ASR 是第 1 版。修订只能改文字，必须提交当前父版本号和原因；并发提交只允许一个成功。片段 ID、音频块编号、时间和切片原因保留。新转写和新任务状态共同提交到 `state.json`，不覆盖原始版本。

修订触发 `report_only` 模式：阅读整理 → 事件提取 → 六维报告，不提取音频、不调用 ASR。报告版本保存输入转写号、文本快照、阅读结果、事件快照、报告、标准版本和事件/报告调用元数据。页面允许原始转写和报告历史回看。旧格式报告如果没有事件快照，不补造当时的事件。

2026-10-14 恢复修复：只为通过事件、报告及证据链校验的结果新增报告版本；失败兜底不作为正式报告。版本新增输入 `asr_status` 与 `report_status`，区分完整输入与受限输入。普通 `example` 只归属内容维度，思维维度需要 `question` 或 `reasoning` 证据；不能仅凭“举了例子”推断思维训练。

## 第四阶段：后台任务

任务 API 是 demo 专用 `/api/jobs`，不等同于主项目协议。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/jobs` | multipart 视频上传，`consent=yes`，返回 202 |
| `GET /api/jobs` | 历史任务，按创建时间倒序 |
| `GET /api/jobs/{id}` | 状态、进度、转写与报告版本 |
| `GET /api/jobs/{id}/media` | 持久化媒体回放，支持 Range |
| `POST /api/jobs/{id}/cancel` | 取消排队或运行中的任务 |
| `POST /api/jobs/{id}/retry` | 人工确认后重试可恢复的失败/部分完成任务；已有版本则固定当前输入，仅重跑文本 |
| `POST /api/jobs/{id}/reanalyze` | 已完成等非运行任务确认费用后，固定现有转写重新分析，保留历史报告，返回 202 |
| `POST /api/jobs/{id}/retranscribe` | 人工确认费用后，复制保留视频创建独立完整转写任务，返回 202；原任务不改写 |
| `GET /api/jobs/{id}/revisions` | 不可变转写版本 |
| `POST /api/jobs/{id}/revisions` | 保存修订并重新分析 |
| `GET /api/health` | 服务健康与六维标准版本 |

任务状态：queued、running、succeeded、partial、failed、cancelled。后台执行器单个，队列容量 32。每个上传文件有独立媒体目录。每次 ASR 成功后保存音频块完成索引，包括没有识别到文字的块。音频提取、读取或 ASR 请求失败即停止，不将失败块记为完成，也不继续文本分析。重试检查原切片方案一致性；完成的块不重复识别。转写全部完成后，先保存原始版本，再调用文本模型。

`asr_status=complete/incomplete/unknown` 与 `report_status=pending/ready/failed` 分别记录转写与报告结果，`failure_stage` 定位失败阶段。文本结果失败时保留可用阅读/事件结果，任务为可重试的 `partial`，不新增正式报告版本；有效的全六维 `insufficient` 不视为系统失败，阅读整理的保守回退也不单独导致分析失败。重试清理当前请求结果和旧结束时间，不借用历史请求元数据；历史版本继续保留。

旧记录只补状态元数据，不改写不可变转写或历史证据。有已知 ASR 跳过警告为 `incomplete`；缺少可靠元数据为 `unknown`。文本重跑和人工改字都不能将这两者改为 `complete`。旧检查点没有原始版本且可靠性不明时，拒绝原地续跑，避免把缺失块误当完成；需确认后用原视频创建独立任务。所有写入路由继续拒绝跨站请求，新任务复制路由只排队，模型请求由执行器处理。

重启不会自动重试正在调用模型的任务；该任务标记失败。排队中的任务会继续。失败可能包含计费未知状态，重试由用户确认。当前不是分布式任务系统，没有跨实例租约。

旧的 `/api/run` 同步接口暂留用于兼容；页面已使用后台任务接口。旧接口不保存历史，不用于第三、四阶段验收。
